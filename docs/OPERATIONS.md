# Running, extending and operating the local build

## First run and everyday use

Use `start-windows.cmd` or `bash scripts/setup.sh`, or the explicit commands in the README. The scripts create a local Python environment, install pinned dependencies, initialise a private runtime directory and load the synthetic demo. They do not register an operating-system service or modify a cloud account.

The default listener is `127.0.0.1:8000`. The desktop launcher opens the private workspace in your browser. A local launch file grants one browser session and expires after five minutes. Restart the launcher to grant a new session. `runtime/api_keys.json` maps API client credentials to tenants. Keep this file and temporary desktop launch files private.

Global CLI options precede the command:

```bash
python -m riskengine --data-dir ./my-private-data --tenant buyer-a init
python -m riskengine --data-dir ./my-private-data --tenant buyer-a import-case my-case.json
python -m riskengine --data-dir ./my-private-data --tenant buyer-a serve --desktop
```

`init` does not silently add a new tenant's key to an existing key file. A trusted operator must manage additional tokens explicitly. The CLI is a local administrative interface and does not offer the isolation boundary of an untrusted remote client. Use the authenticated API for remote-client contracts after completing the production deployment work.

## Runtime locations

| Location | Contents |
|---|---|
| `runtime/riskengine.sqlite3` | Durable cases, evidence, assessments, documents metadata, source policies, jobs and audit |
| `runtime/api_keys.json` | Random local bearer credentials; not included in release |
| `runtime/snapshots/` | Tenant/case-scoped captured source files, definitions and capture receipts |
| `runtime/documents/` | Opaque private document bytes; exact path is managed by the API |
| `runtime/demo-assessment.json` | Synthetic result generated by `demo` |
| `runtime/demo-report.html` | Standalone synthetic HTML report |

Runtime data is outside the static web directory. Source permissions are enforced at application boundaries, but direct filesystem access by an administrator remains privileged. Use OS access controls and appropriate device encryption.

## Activate a source

1. Find its exact record in `config/sources.json` and inspect the source-specific metadata/terms.
2. Record the publisher, licence URL, attribution, reviewed date and authorised processing, retention, raw display and derived display choices.
3. Configure the exact adapter endpoint and expected schema. For restricted feeds, put secrets in environment variables and reference their names in `auth_env`; never place credentials in URLs, logs or JSON values.
4. Test a small bounded capture and inspect completeness/errors, units, date semantics, duplicate IDs and raw hashes.
5. Configure/review the relevant property-specific mapping and coverage evidence. A source may be collectable yet not eligible for an assessment.

Copy the registry to a private working configuration and set `RISK_SOURCES_PATH` if you do not want to alter the packaged baseline. A false/missing `retain_raw` right causes `POLICY_REVIEW_REQUIRED` before source-byte capture. Other false rights prevent processing or display independently. `enabled` is a scheduling preference, not a permission bypass.

The package starts with one reviewed ACT crime source. Other entries intentionally expose pending rights or access. An updated crime asset can be discovered through its catalogue metadata, but coverage/vintage must still be checked.

## Bounded collection and durable jobs

```bash
python -m riskengine collect demo-house act_crime_statistics --bounds examples/kingston_crime_bounds.json --max-records 1000
python -m riskengine collect demo-house act_crime_statistics --bounds examples/kingston_crime_bounds.json --enqueue --idempotency-key crime-kingston-capture-001
python -m riskengine worker --max-jobs 10
python -m riskengine jobs
```

A repeated idempotency key must identify the same payload. Retrying a changed query under the same key is an error. A worker claims a lease before processing. Transient fetch failures retry with bounded attempts; blocked/policy/access outcomes are recorded as explicit work results rather than endless retries. For scheduled use, arrange an authorised external scheduler to invoke the bounded worker and inspect job/source-health states. This release does not install such a scheduler.

`bounds` values depend on adapter. ArcGIS supports a valid `bbox`, `in_sr`, `out_sr` and `where`. A source-level attribute filter cannot establish a clean hazard result without an appropriately reviewed complete mechanism scope. Crime supports `area`, `start_period`, `end_period`. RBA/SDMX series support period bounds. Unsupported scope keys are rejected.

## Import private evidence

Use the dashboard's Evidence tab to upload a PDF/text/JSON/image document, within the 5 MB limit. Uploaded bytes are inert evidence with `extraction_status: NOT_ASSESSED`. Record page/section references and review findings before importing typed observations. Do not mark an extracted assertion as reviewed merely because an LLM wrote it.

New private evidence is stamped with server receipt time. To include it, explicitly advance the case's `as_of` and create a new assessment. The dashboard's “Use evidence received up to now” checkbox does this visibly. CLI users can use `assess ... --advance-as-of`. A historical assessment must not silently use later receipts.

## Verify and replay

```bash
python -m pytest
python -m riskengine demo
python -m riskengine replay "ASSESSMENT-ID"
```

Keep the release ZIP and the input snapshots for every material assessment. The decision hash includes runtime geometry-library versions. A different Python/GEOS/PROJ version may legitimately produce a different hash; do not describe it as exact replay under the original runtime. Windows/macOS wheels and the Docker image need their own verification before claiming platform-identical output.

`scripts/browser_smoke.cjs` is an optional full-browser acceptance script requiring a separate Playwright/Chromium installation and a running demo service. It is not a production dependency. See `VERIFICATION.md` for the actual browser execution status in this environment.

## Backup and restore

Stop the application and workers before a simple directory copy. Back up the **whole private runtime directory**, including the SQLite database, any SQLite journal/WAL files present, raw snapshots and documents. Also retain the exact source/rule configuration and release archive. Keep credentials separate when exporting a case for a different audience.

For an online backup, use SQLite's supported backup mechanism and coordinate raw-file capture; copying only the main `.sqlite3` while writes are active is not a validated backup. No automated backup/restore service is installed by this package. Restore into a private directory, run database integrity checks, validate raw-file hashes and replay a known assessment before relying on the restored instance.

Source policy restrictions block subsequent processing/display/capture. They do not automatically delete already retained bytes. A production retention/deletion workflow must identify raw files, evidence, derived reports, backups and legal retention obligations together; do not implement a partial delete and claim comprehensive erasure.

## Docker packaging

`Dockerfile` and `compose.yaml` are supplied. Docker was not available for execution verification here. Build and test it in your own environment before relying on it:

```bash
docker compose build
docker compose run --rm property-risk python -m riskengine init
docker compose run --rm property-risk python -m riskengine demo
docker compose up
```

Ensure the mounted runtime directory is writable by the container's non-root user and remains private. The host binding is loopback. A production container also needs a reviewed base image digest, vulnerability scanning, resource limits, secrets handling and backup controls.

## Extend the engine without losing determinism

For a new source, implement capture/parsing, retain source bytes and provenance, add bounded/error fixtures and define the exact semantic mapping. For a new signal, update the required manifest, prerequsites and supported payload contract, then add a meaningful acceptance fixture that would catch a wrong conclusion. Do not add an opaque LLM output directly to the score.

For a new model, state the target first: event probability, depth, annual loss, market price or travel time are different quantities. Specify training/validation geography and periods, calibration and uncertainty, data permissions, drift monitoring and how the output enters a buyer decision. Deterministic execution does not make a poorly calibrated model correct.

When rules change, increment the relevant rule/release version, retain prior configurations and rerun the reference fixtures. Changes to a required-check denominator require explicit review because they change completeness claims. Confidence and opportunity policy must remain independent from substantive concern priority.

## Release maintenance

The runtime uses the compiled JSON configuration and does not need the original uploaded workbooks. `scripts/compile_inputs.py` can regenerate the baseline from the bundled `reference/ingestion_catalogue.json`; reviewed source overrides must be reapplied. `scripts/generate_input_register.py` regenerates the readable complete register. Diagram regeneration uses Graphviz and optional pypdf, which are documentation tools rather than runtime dependencies.

`requirements.lock` pins the executed Linux dependency versions. It is not a supply-chain signature or a guarantee of vulnerability-free packages. Keep independent package hashes/signing and platform-specific lock/CI verification in a production release process.
